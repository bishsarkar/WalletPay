How IBM Bob Was Used in This Initiative

In the past, I utilized IBM Bob for various technical tasks, such as refactoring code, modernizing existing codebases, and resolving production issues. For this specific initiative, my objective was to explore a new technology and business area where I had limited exposure, evaluating how effectively IBM Bob could facilitate the entire lifecycle—from initial information gathering, option analysis, and comparative judgment, to final system design and production-quality code generation, all without leaving Bob.

The workflow was executed through the following structured components:

  • Two Custom Modes and several Bob’s inbuilt modes
  • A Specification-Driven Development (SDD) File: A structured requirements document produced in Bob’s Plan mode, comprehensively covering: user stories, acceptance criteria, technical constraints, and success metrics
  • Leveraging this single specification, Bob’s create-plan skill generated a structured, 10-sub-task delivery plan detailing the exact scope, expected outcomes, and ordered action items for each sub-task. Consequently, every subsequent implementation sprint remained strictly anchored to a verified, reviewable execution plan.
Overview
The Problem:

Building a compliant payment system requires months of engineering. Identity verification, KYC/AML enforcement, custodial wallet management, webhook security, audit logging The WalletPay PoC was built to answer a direct question: can IBM’s AI-assisted development tooling compress that timeline without sacrificing quality?.

Our Solution:

WalletPay is a compliance-first stablecoin payment platform on Base L2 (USDC). Five integrated workflows delivered:

  • KYC / AML Onboarding — Persona photo-ID + selfie; OFAC stub; wallet gated until approved
  • P2P USDC Transfers & Utility Bill Payment — send by email, phone, or wallet; alias resolution; on-chain settlement
  • AI Chat Assistant — every feature via natural language through IBM watsonx Orchestrate
  • Fabric Audit Trail — every confirmed transfer anchored on Hyperledger Fabric 2.5; 3-org consortium; RegulatorOrg on independent channel
  • What Next — Real OFAC/sanctions provider, Fraud/Anomally detection, MetaMask / WalletConnect for self-custodial wallet

Benefits and Features
Bob's Impact
  • Spec-driven delivery: WalletPaymentSpec.md → openapi.yaml → 10-sub-task plan → full implementation — no manual scaffolding
  • Architecture decisions documented: Base L2 vs Arbitrum, USDC vs USDT vs DAI, MCP vs OpenAPI import — structured comparison tables, reviewable and revisable
  • Critical bug caught in review: Circle webhook RSA vs HMAC-SHA256 — would have left all transfers permanently pending in production
  • Test-driven development: 104 tests across 7 suites written alongside implementation; 80% line/function coverage enforced in CI
  • Multi-modal workflow: Plan → Agent → Code Reviewer → Simplify — each mode used for its purpose; no external doc tab-switching
  • Fabric integration end-to-end: network topology, chaincode, API client, Phase 2 multi-channel architecture — 8 production issues diagnosed and resolved

Quality Highlights
  • Compliance-first: requireKYC middleware blocks all transfers until identity approved; every decision logged to audit_logs
  • Webhook security: RSA asymmetric (Circle) + HMAC-SHA256 (Persona); 401 on failure, zero state change
  • Injection hardening: UUID format guard on X-Behalf-Of-User before any DB query
  • Immutable ledger: Fabric AND endorsement policy — no single org forges a record; RegulatorOrg sees aggregated SummaryRecord only, never transaction PII
